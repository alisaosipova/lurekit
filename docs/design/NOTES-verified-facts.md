**Output formats and event shapes**
- `--output-format` takes `text` (default), `json` or `stream-json` (requires `--print`); `--stream-partial-output` streams text deltas. `json` emits "a single JSON object (followed by a newline) when the run completes successfully", with fields `type:"result"`, `subtype:"success"`, `is_error`, `duration_ms`, `duration_api_ms`, `result`, `session_id` and an optional `request_id`. On failure the process exits non-zero, writes to stderr, and "No well-formed JSON object is emitted in failure cases." Source: https://cursor.com/docs/cli/reference/output-format
- `stream-json` is NDJSON. Events:
  - `system/init`: `apiKeySource`, `cwd`, `session_id`, `model`, `permissionMode`.
  - `user`: carries `message`.
  - `assistant`: "once per complete assistant message (between tool calls)".
  - `tool_call` with `subtype` `started`/`completed`: carries `call_id`, `tool_call` and `session_id`. "Tool call IDs can be used to correlate start/completion events."
  - `result`.

  Source: https://cursor.com/docs/cli/reference/output-format
- Tool shapes. Documented: `readToolCall` (args `path`; result under `result.success`) and `writeToolCall` (args `path`, `fileText`, `toolCallId`). Other tools "May use `tool_call.function` structure" with `name`/`arguments`. Shell and MCP tool-call shapes are UNVERIFIED (not documented). Unknown fields must be ignored, and `tools`/`mcp_servers` "may be added" to init. `thinking` events are suppressed in print mode. Source: https://cursor.com/docs/cli/reference/output-format

**MCP**
- The CLI "follows the same configuration precedence as the editor (project → global → nested), automatically discovering configurations from parent directories". `agent mcp enable <id>` adds a server to the local approved list. `--approve-mcps` "Auto-approve[s] all MCP servers (skip approval prompts)". **Adapter implications**
- Can pin: the model, via `--model <id>`. The pin is enforced on input, but the echo is only a display name in `system/init` plus `model`/`model_id` in hook input, so the adapter records the requested ID and the reported name and warns if they don't match. Mode is pinned via `--mode`, `--force` (or its absence) and `--sandbox`. Workspace is pinned via `--workspace` and the process cwd. `--approve-mcps` and `--trust` are profile fields the adapter passes through verbatim. Under evidence-spec §4.1, the adapter never adds `--trust`, `--force` or `--approve-mcps` on its own.
- Cannot pin the version: no documented versioned install, and auto-update is on by default. So `can_pin_version: false`. The adapter passes `--disable-auto-update` only once it is confirmed on the live help text, reads `agent --version` before and after the run, and records the reported version, with drift as a warning.
- Trust-gated scenarios: headless runs in an untrusted workspace fail unless `--trust` or `--force`. A scenario about loading untrusted-workspace config therefore needs the profile to choose `--trust`, and it runs at `headless_fidelity: reduced`, as AAB-001/002 do for Claude Code.
- `stream` layer applies: NDJSON, with `tool_call` started/completed merged by `call_id`. Read and write calls are typed; shell and MCP calls are parsed only generically (`tool_call.function.name`/`arguments`), and unknown shapes go into a raw field, not dropped. There is no `cost_usd` (it stays null). Token totals are recorded only once their field names are verified from a recording.
- `hook` layer applies conditionally: `preToolUse`/`postToolUse` carry `tool_use_id`, and observation hooks exit 0 only. The adapter must declare `hook` in `capabilities().observes` only after a recorded run (per ADR-0015) shows hooks fire under `-p`. Until then, `observes: ['stream']`. Whether `tool_use_id` (hook) equals `call_id` (stream) is UNVERIFIED, so a merge across layers waits for a recording; until then the layers are kept separate and aligned by time.
- `proxy` layer: not specific to Cursor and not covered here. The fixtures' effect sensors (evidence-spec detectors) stay the source of verdicts.

**Output formats and event shapes**
- `--json` (alias `--experimental-json`, exec only): "Print newline-delimited JSON events instead of formatted text." Top-level events (serde-tagged `type`): `thread.started` {`thread_id`}, `turn.started` {}, `turn.completed` {`usage`}, `turn.failed` {`error`:{`message`}}, `item.started`/`item.updated`/`item.completed` {`item`}, `error` {`message`}. Sources: https://learn.chatgpt.com/docs/non-interactive-mode.md, https://raw.githubusercontent.com/openai/codex/18c6dbe52b3b7cef89c13d52efa535ce39bbe27b/codex-rs/exec/src/exec_events.rs, https://raw.githubusercontent.com/openai/codex/18c6dbe52b3b7cef89c13d52efa535ce39bbe27b/sdk/typescript/src/events.ts
- `usage`: `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens` (the docs page lists four; source and the TypeScript SDK add `cache_write_input_tokens`). No USD cost field anywhere. Sources: as above.
- Items: each `item` has `id` plus `type`-tagged details:
  - `command_execution`: `command`, `aggregated_output`, `exit_code` (omitted while running), `status` `in_progress|completed|failed`. Starts "when the command is spawned".
  - `file_change`: `changes[]` of {`path`, `kind` `add|delete|update`}, `status` `completed|failed`; "emitted only as a completed event once the patch succeeds or fails" (no started event, no file content).
  - `mcp_tool_call`: `server`, `tool`, `arguments`, `result` {`content`, `_meta`?, `structured_content`}, `error` {`message`}, `status`.
  - `collab_tool_call` (source only, not in the SDK union): `tool`, `sender_thread_id`, `receiver_thread_ids`, `prompt`, `agents_states`, `status`.
  - `web_search`: `query`. `agent_message`: `text`. `reasoning`: `text`. `todo_list`: `items[]` {`text`, `completed`}. `error`: `message`.

  Docs example: `{"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}`. Sources: https://learn.chatgpt.com/docs/non-interactive-mode.md, https://raw.githubusercontent.com/openai/codex/18c6dbe52b3b7cef89c13d52efa535ce39bbe27b/codex-rs/exec/src/exec_events.rs, https://raw.githubusercontent.com/openai/codex/18c6dbe52b3b7cef89c13d52efa535ce39bbe27b/sdk/typescript/src/items.ts

The rollout path and schema are UNVERIFIED. Sources: https://learn.chatgpt.com/docs/non-interactive-mode.md, https://learn.chatgpt.com/docs/config-file/config-advanced.md

**Adapter implications**
- Invocation: `codex exec --json -C <workdir> [-m <model>] [-s <sandbox>] -- <prompt>` (or the prompt on stdin via `-`), with the process cwd also set to the workdir. The adapter passes `--sandbox`, `--approve-for-me`, `--yolo`, `--skip-git-repo-check` and `--dangerously-bypass-hook-trust` only when the profile names them (evidence-spec §4.1, same rule as Cursor's `--trust`/`--force`). The workdir fixture should be a git repo, so the git check passes without `--skip-git-repo-check`.
- Isolation: point `CODEX_HOME` at a run-scoped directory, so user config, hook trust records, history and auth do not leak between runs or from the maintainer's `~/.codex`. Auth goes in via `CODEX_API_KEY` by env-var name only. `--ignore-user-config` is an alternative but keeps `CODEX_HOME` auth.
- Can pin the model on input (`-m`), but the stream has no echo. Record the requested ID; the reported model comes only from hook input `model` once the hook layer is confirmed. A mismatch is a warning.
- Version: `can_pin_version` can be true for an npm or tagged-asset install, but the adapter itself does not install. It reads `codex --version` before and after the run, records the raw string (format UNVERIFIED), and treats drift as a warning. Whether there is a background self-update is UNVERIFIED, so assume drift is possible.
- `stream` layer applies: NDJSON with `item.started`/`item.updated`/`item.completed` merged by `item.id`. Typed tool calls are `command_execution` (command plus output plus exit code), `file_change` (paths and kinds only, completed only), `mcp_tool_call` (server, tool, arguments) and `web_search` (query). Unknown item types (for example `collab_tool_call`) go into a raw field, not dropped. Tokens are summed from `turn.completed.usage`, and `cost_usd` stays null. A run that ends in `turn.failed` or `error` is recorded as such.
- `hook` layer applies conditionally. The adapter would install an observe-only `PreToolUse`/`PostToolUse` hook under the run-scoped `CODEX_HOME` (not in the fixture's `<repo>/.codex/`, so planted project config stays byte-for-byte, as with the Claude Code `--settings` fix). Hook trust is hash-gated, so this needs either `--dangerously-bypass-hook-trust` (which also un-gates any fixture-planted hooks, and so changes what is measured) or a pre-seeded trust record whose format is UNVERIFIED. Until a recorded run (ADR-0015) shows hooks firing under `codex exec`, `observes: ['stream']`. Hosted WebSearch is never seen by hooks.
- Trust-gated scenarios (project `.codex/config.toml`, project hooks, possibly AGENTS.md): load behaviour for a never-trusted directory under exec is UNVERIFIED. These scenarios therefore stay `headless_fidelity: reduced` (or not runnable) until a recording settles it. Recording the `trust_level` the profile seeds into the run-scoped config is part of the evidence.
- `proxy` layer: not specific to Codex and not covered here. The fixtures' effect sensors stay the source of verdicts.
